## What the layout-heavy document changed

`KB-ENG-005` (generated by `scripts/make_complex_pdf.py`) is a two-page rate card with two
ruled tables, two-column prose and running headers; seven of the 41 gold cases ask for facts
that live in its table cells.

The first run of this comparison scored Docling **0/5** on those cases. That was a bug in
the gold set, not a finding: our extractor renders a row as `checkout-api 1,200 180 ms`
while Docling renders it as `checkout-api, Funded RPS = 1,200`, and the gold evidence was
written as a literal substring of ours. Table cases now carry `evidence_terms` - a set of
terms that must all appear in the retrieved chunk - so the score measures retrieval instead
of an extractor's punctuation.

With that fixed, on hybrid retrieval: production parent-child **0.878** Hit@1 (CI 0.74-0.95)
against Docling's **0.854** (CI 0.72-0.93), with Docling using fewer chunks (34 vs 56) for
the same corpus. **The intervals overlap, so this corpus does not separate them.** Docling's
table serialisation is arguably better - it keeps the row label with each cell value, which
is exactly what a naive text dump loses. The reason production does not use it is
operational (D-20): it pulls in PyTorch and layout models, and every document here is text
we control. On a corpus of scanned or genuinely complex PDFs that trade would look different,
and this comparison is the place where that would show up.
