## What the layout-heavy document changed

`KB-ENG-005` (generated by `scripts/make_complex_pdf.py`) is a two-page rate card with two
ruled tables, two-column prose and running headers; seven of the 41 gold cases ask for facts
that live in its table cells.

The first run of this comparison scored Docling **0/5** on those cases. That was a bug in
the gold set, not a finding: our extractor rendered a row as `checkout-api 1,200 180 ms`
while Docling renders it as `checkout-api, Funded RPS = 1,200`, and the gold evidence was
written as a literal substring of ours. Table cases now carry `evidence_terms` - a set of
terms that must all appear in the retrieved chunk - so the score measures retrieval instead
of an extractor's punctuation.

With that fixed, production parent-child and Docling were indistinguishable (0.878 vs 0.854
Hit@1 on hybrid, overlapping intervals). Docling's table serialisation was nonetheless the
better one: it keeps the row label with each cell value, which a naive text dump loses - and
the answering suite then showed the cost of losing it (case L04 read a SEV1 value off the
row above; see [`analysis.md`](analysis.md)).

**Table rows now carry their own labels.** The PDF parser reads each cell's x position,
recognises a table as lines of three or more runs whose columns repeat, and rewrites each data
row as `Tier 2 - platform (SEV1): Hours = 24/7; Acknowledge within = 10 minutes; ...` - one
block per row, so no chunk boundary can separate a value from its row or column. Re-run, the
production chunker scores **0.927** Hit@1 (CI 0.81-0.97), MRR 0.963, against 0.878 / 0.931
before. The intervals still overlap Docling's, so the honest claim is "no worse, and the
answer step is no longer asked to align columns by eye", not "better than Docling". Docling
stays out of production for the operational reason in D-20: it pulls in PyTorch and layout
models, and every document here is text we control.
