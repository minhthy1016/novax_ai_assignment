# Embedding model comparison: nomic-embed-text vs nemotron-3-embed-1b

Generated by `python -m evaluation.embedding_eval` on 2026-09-24. Same production
parent-child chunker, same gold set (`retrieval_cases.jsonl`), same access control and
scoring as [`chunking.md`](chunking.md); only the embedding model changes.

**Confidential documents are excluded** (`KB-HR-002`, and the one case that asks about it).
Embedding with NIM sends document text to NVIDIA's API, and confidential material may never
leave the machine (D-15). Both models are scored on the same 40 cases over 10 documents
(58 chunks).

local model.

## What it says

* **Vector-only, nemotron ranks better:** Hit@1 0.950 vs 0.825, five more cases with the
  right passage first. The intervals overlap (0.83-0.99 vs 0.68-0.91), so on 40 cases this
  is a strong hint, not a proven difference.
* **In production mode (hybrid: vector + BM25), there is no difference:** both 0.925 Hit@1
  and 0.963 MRR. Keyword search already recovers the cases where nomic's vectors rank the
  right passage second, so the better embedding buys nothing measurable in the mode the
  system actually uses.
* **The costs of nemotron are real:** document and query text leave the machine (never
  allowed for confidential material, so a second, local index would still be needed for
  it); ~0.6 s added to every query embedding; 2048 dimensions need `halfvec` for an HNSW
  index, and each vector is ~2.7x larger than at 768-d (4,096 vs 1,536 bytes as `halfvec`),
  which would grow the ~84 GB index in D-60 to roughly 200 GB.

**Decision unchanged:** nomic-embed-text stays the index model (D-20). Revisit if the corpus
grows in ways keyword search handles badly (paraphrased questions, other languages), or if
a hybrid run on a larger gold set shows a gap. Running nemotron self-hosted on the GPU tier
would remove the egress and latency objections, leaving only the storage cost.
